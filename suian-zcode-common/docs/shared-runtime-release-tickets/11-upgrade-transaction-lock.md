# GUL-02：网关切换事务幂等锁

**状态**：用户已确认（2026-10-21）；已发布为 #135；可以立即实施。

## 问题与交付行为

setup.ps1 无任何防重入。多入口并发是现实场景：多个插件的安装技能各自引导 Install/Restart、depcheck Toast 修复提示词引导重跑、用户手动执行。并发执行的破坏不在重复 shutdown（其本身近乎幂等，计划任务有 IgnoreNew），而在 activate 交叉：`active-gateway.json` 原子写是最后写者赢，两个 setup 各自 activate 不同 buildId、各自健康确认自己期望的版本，其中一个必然 mismatch 进入回退，回退又写回各自快照——活动记录被踩、网关被反复重启。

本票交付：Install/Restart/Remove 的切换事务（从状态检查、shutdown 到健康确认或回退完成）由网关数据目录内的独占句柄锁文件（upgrade.lock）保护；第二个实例在锁被持有时结构化失败并报告持锁进程，不触碰任何文件；持锁进程崩溃或被杀时锁由操作系统自动释放，无需基于时间的陈旧判定。Status 只读操作不加锁。

## 负责模块

common 的 setup.ps1（锁获取/持锁范围/释放）；setup.test.mjs 新增并发与崩溃释放契约测试。

## Blocked by

无（可立即开始；与 GUL-01 改不同文件，无实施顺序依赖）。

## 接口与约束

- 锁文件位于网关 DataDir（与 config.json 同目录），作用域即网关身份；用 Windows 独占句柄（FileShare.None）实现"进程退出即解锁"，不引入 staleAfterMs 类时间参数。
- 锁持有范围覆盖切换事务全程，含 GUL-03 加入后的忙退避等待段，防止"两个升级都在等空闲、空闲后双双发出 shutdown"的惊群；暂存候选（--deploy）不在锁内，保证幂等的部署阶段可并发无害。
- 拿锁失败是明确失败：结构化输出（含持锁方 pid 类信息）与非零退出码，不静默当作成功，也不排队等待。
- 锁获取/释放不得污染正常路径输出；异常退出路径同样释放（脚本 throw、回退完成、候选失败撤销）。

## 验收条件

- [ ] 测试：事务进行中第二个实例拿锁失败，输出含进行中标识，未修改任何配置、任务或部署记录。
- [ ] 测试：持锁进程退出（含被强杀）后锁立即可被下一实例获取，无需任何清理参数。
- [ ] 测试：Status 只读操作在锁被持有时正常工作。
- [ ] 测试：锁内事务走失败回退路径后锁已释放，后续实例可正常重试。
- [ ] 既有 Install/Restart/Remove 场景测试全绿，正常路径无行为变化。

## 验证与完成边界

验证在 setup.test.mjs 的隔离 fixture 内完成（真实子进程、临时目录），不修改真实用户环境。锁的正确性以进程句柄语义为准，不承诺跨主机或跨用户场景。
