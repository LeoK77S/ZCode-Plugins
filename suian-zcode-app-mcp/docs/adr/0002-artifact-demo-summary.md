# 工件 demo 使用可累积的简略摘要，完整版唯一投影等待上游

**状态**：2026-10-11 已接受摘要范围、触发时点、原生只读侧栏，以及 SQLite 历史快照和缺失时不阻断后续操作的规则。2026-10-12 已在本地实施；后续验证见 [开发验证](../artifact-demo-verification.md)。

## 背景与决定

3.14.5 的隔离核验已证明 UserPromptSubmit.additionalContext 不能满足每请求唯一最新尾部投影。用户本轮接受先交付 demo：自动上下文只包含要求登记、维护工件的管理提示词，以及种类、条数等统计信息；允许它们在运行时上下文中累积。完整工件状态继续独立持久化，通过增量工具维护。

[ADR 0001](0001-session-artifact-projection.md) 中的完整版唯一投影目标继续保留，已拆为 [#36](https://github.com/ONEGAYI/ZCode-Plugins/issues/36) 并标记 wait-for-upstreaming。四张现有开放票 #28–#31 已改为 demo 范围，保留 enhancement、移除等待上游标签；已回读核验。

## 影响与取舍

demo 不以自动上下文的唯一性为实施前置条件，也不自动反复附带完整条目。摘要在每次用户提交时生成；get/set 回执更新当前 revision 和分类统计。同一轮工具续跑或重试可保留旧摘要，Agent 需要完整状态时调用 get_artifacts。get 必须每次读取最新真实状态，不能返回上次投影或进程缓存作为当前工件。

用户允许摘要累积，不等于授权清理旧运行时历史或修改 ZCode。demo 包含 Desktop 本地会话的原生只读工件侧栏，旧版继续保留工具和摘要；UI 按新版宿主能力条件提供。UI 插件能力不解除完整版请求投影的上游依赖。

## 分叉决定与待验证能力

用户明确要求分叉时的准确快照，并进一步要求先探索能力边界再考虑方案。没有接受子会话空状态或首次访问时复制父最新状态；本轮不把分叉自动移出 demo。

此前探索以执行分叉操作时冻结父状态为基准。用户随后提出历史断点方案：每次 Stop 保存不可变工件快照，分叉按选中的已完成生成轮定位快照并初始化子状态。该方案无需在分叉通知到达时读取父当前状态，也不以新增分叉前 Hook 为前提。

用户已选择插件自有 SQLite 保存不可变快照，并建立“父会话 ID＋断点消息 ID → 快照 ID”的映射。内容无变化时可复用快照，但每个断点仍登记映射；不引入独立 Git 仓库。

3.15.1 源码已核实常规成功结束路径等待 Stop，随后持久化最终消息断点并发布 TurnComplete；分叉目标要求 completedSuccess。本轮隔离运行已将 Stop 的 turnId 对应到只读消息 anchor.turnId 和完成消息 ID，再用子 forkOrigin 中的原始父 ID/目标消息 ID 定位历史快照。

**已验证**：父状态 A 完成后改为 B，从 A 断点原生分叉，子 SessionStart 首次读取 A，且读取早于分叉响应；无变化仍登记新断点；同轮两次 Stop 各绑定不同消息，最终断点分叉读取第二份；缺映射时分叉被接受，子状态可继续读写并完成新一轮聊天。探针使用隔离 SQLite 和合成模型，未实施生产 get/set 或运行真实 Desktop 侧栏。证据见 [分叉核查](../artifact-host-fork-audit.md)。

不能将“可分叉”概括为“一定触发 Stop”：源码有 automationCreateLimitReached 分支，显式跳过 Stop 后仍以 success 收口。旧会话、该特殊路径或 Hook 失败可能缺少快照。

**缺失时行为已确认**：保留原生分叉的子会话，工件首次 get/UI 明确报告 snapshot_missing，不复制父最新状态，也不把空集合表述为准确继承。缺失提示不阻断分支或后续工件操作；子会话仍可独立新增、更新、删除和读取自身工件。提示属于继承诊断，不是永久禁止使用工件区的错误门禁。

历史断点路线适用于已测原生稳定分叉入口，无需先改为插件受控分叉。原有操作时快照研究仍保留为不同继承基准的历史证据。本轮未实施新的分叉工具。

技术依据及原有核验边界见 [工件区设计](../artifact-zone-design.md) 与 [宿主核验](../artifact-host-capabilities.md)。

## 2026-10-12 实施修正

公开源码把 MCP clientInfo.version 接到应用版本，但本机 3.15.1.8093（构建 f18d6db7）实测仍报告 CLI 0.16.9。同一原生 MCP 进程收到 Desktop 的 ZCODE_APP_VERSION=3.15.1。门控优先使用该应用版本环境变量，缺失时才读取 ZCode 客户端握手版本；同时核对 MCP Apps MIME。页面桥接版本不参与比较。

原生页采用宿主已公开的 window.zcode 兼容桥，只需调用 get_artifacts 与响应主题，不增加构建依赖。真实 Desktop 已验证刷新、父子会话隔离、缺快照诊断、空状态和存储错误。未连接目标会话 MCP 的首开可能在宿主签发页面凭证前失败；插件不替宿主启动模型轮，连接就绪后重新加载。真实模型主动维护评估仍独立保留。

用户随后要求进一步缩短自动管理提示词：每次提交只保留一句及时登记或更新工件的入口，指向原生 set_artifacts；详细维护规则放到 get/set 工具描述。统计和必要的 snapshot_missing 诊断继续保留，容量计算维持既有固定表示，避免入口文案变化影响存储边界。

## 2026-10-12 工件简表注入追加决定

用户进一步允许 UserPromptSubmit 注入部分工件简表。此决定替代上文“自动上下文仅入口和统计”的限制，不改变可累积摘要与完整版唯一投影之间的边界。

自动简表最多 20 条，整个注入内容最多 9000 个 Unicode 码点。用户确认每个非空类别先预留最新 3 条（不足则全取），再按全局更新时间补足；字数不足先保住各类最新 1 条。时间序胜出的类别仍可以多于 3 条，保证不会因最近工件集中于一个类别而完全挤出其它类别。

超出预算只裁剪显示，明确省略数量和字段截短；完整引用与状态仍通过 get_artifacts 读取。工件存储已在前次列表改版中取消数量与完整表示容量上限，自动注入上限不恢复存储限制。规则与验证入口见 [工件规格](../artifact-zone-spec.md)。
