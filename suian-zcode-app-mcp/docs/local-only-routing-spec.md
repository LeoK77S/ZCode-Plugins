# local-only 补丁多版本自动路由规格

**范围**：2026-10-22 用户确认实现自动路由并补齐规格。本次实现安装期的档案选择和旧记录兼容；真实支持清单仍只有 Windows 3.16.2.8769 的既定包。新增真实版本须单独适配和验收。

前置能力见[首轮规格](local-only-spec.md)和[开发集成总验收](local-only/09-development-acceptance.md)，长期决定见 [ADR 0004](adr/0004-local-only-patch-routing.md)，实施验证见[路由验证记录](local-only/10-routing-acceptance.md)。

## 目标与成功标准

新增 ZCode 适配时，新工具携带新旧档案，自动为用户的实际安装包选择对应注入规则。旧包不要求升级 Desktop，也不要求 Agent 手选脚本。旧安装的备份和状态可继续用于识别、同包补丁升级及还原。

成功标准：两个合成包可在同一注册表中独立完成 prepare、apply、status、restore；历史格式 1 记录可读取；跨包候选、损坏记录及降级请求在修改目标前失败；现有真实包的 v3 补丁输出字节不变。合成第二包只证明路由机制，不代表第二个真实版本已获支持。

## 用户故事

1. 使用旧版 Desktop 的用户更新公共插件后，仍能管理已支持的旧包补丁。
2. 使用新适配包的用户沿用 setup 的 local-only 流程，不需要挑选适配脚本。
3. 已打补丁的用户希望工具从状态记录找到原版身份，继续诊断、升级补丁或还原。
4. 升级了 Desktop 的用户希望旧候选和旧备份被拒绝，避免覆盖新包。
5. 维护者希望新增档案时旧档案及回归继续随包保留，失败能定位到具体档案。

## 档案与模块职责

**适配档案（profile）**：一个经过验证的原始发行包及其注入实现。档案 ID 稳定，按该包独立维护补丁修订号。应用版本、补丁修订号和元数据格式版本分别表示不同含义，不相互比较。

| 模块 | 责任 |
| --- | --- |
| common `local-only/profiles/` | 每包身份、独立补丁修订号、asar 入口与注入函数；现有 v3 注入原样迁入 |
| common `local-only/profiles.mjs` | 随包静态注册表及唯一精确匹配；先按平台、exe FileVersion、原版 app.asar SHA-256 选档案 |
| common `local-only/patch.mjs` | 四个命令共用识别；元数据读取、候选绑定、备份、升级与还原；保留真实退出码 |
| common `local-only/patch-env.mjs` | 通用备份/状态文件约定和退出码；兼容既有首包注入接口的导入 |
| common `local-only/lab-env.mjs` | 继续提供现有单包 lab；身份引用档案，不再由 lab 拥有生产身份 |
| common `build-release.mjs` | 分发注册表和档案目录；release.json 记录全部文件摘要 |
| setup / Agent | 继续调用统一 CLI，解释回执中的 profileId；不重复实现选择规则 |

当前布局为 Windows 的 `ZCode.exe` 和 `resources/app.asar`。本次不扩展其它平台的磁盘布局。架构不同但版本相同的包仍由完整摘要区分，不依赖当前 Node 的架构猜测 Desktop 架构。

## 识别与状态契约

| 输入 | 行为 |
| --- | --- |
| 无状态的原包 | 用实际平台、exe 版本、当前 asar 摘要唯一命中档案 |
| 已 patch，格式 2 状态 | 原版摘要选择档案，profileId、platform 和目标 exe 版本必须一致；当前摘要须属于记录原版或补丁版，才允许对应操作 |
| 历史格式 1 状态，无档案字段 | 按记录的原版摘要和实际 exe 版本精确映射；不按列表顺序兜底；只读命令不改写记录 |
| 状态损坏、字段缺失或未知格式 | `invalid_metadata`，退出码 17；保留文件并明确报错，不按“无状态”继续 |
| 有档案字段但不匹配 | 拒绝，不回退格式 1 的隐式映射 |
| 未知平台/版本/摘要或多档案命中 | 不支持，不能自动选最新档案、模糊匹配锚点或切换模式 |

status 保留原接口语义：可读取但未知的包返回 `ok:true, supported:false`；输入无法读取或元数据损坏返回失败。已知包回执增加 profileId。patched 的 patchInfo 只比较本档案的 patchVersion，较旧时提示 upgradeAvailable；较新时不提供降级路径。

状态文件名和备份后缀保持不变。新候选、新应用状态为格式 2，加入 profileId 和 platform，保留既有摘要、版本和注入清单字段。旧格式 1 候选继续按原包身份识别；未成功写入前不迁移旧记录。旧工具不保证能读取新格式，回退工具版本不构成补丁降级操作。

## 命令行为

1. **prepare**：只读目标。原版直接生成对应档案的候选；旧修订补丁只从摘要正确的原版备份生成升级候选。当前或更新修订的已 patch 目标不重复叠加注入。
2. **apply**：重新识别当前目标和候选所属档案，核对候选的 ID、平台、入口、路径与修订号。所有绑定检查先于自动还原、备份及替换。候选高于随包档案修订号时拒绝；已安装补丁高于候选时拒绝降级。
3. **同包升级**：仅比较同一档案修订号。旧状态确认当前字节、备份正确后，restore → apply；新状态写入格式 2。不同档案的修订号没有大小关系。
4. **restore**：必须有有效状态和仍可识别的原包档案。当前包被升级、原版摘要与档案不符或备份错误时拒绝。符合记录的原版可清理残留状态；符合记录的补丁版可还原。

CLI 参数保持 `status/prepare/apply/restore --target` 与现有候选参数。删除生产 CLI 的 `--package-identity` 覆盖入口：任意身份 JSON 无法提供新包的注入规则，不能用它绕过支持清单。合成测试通过 JS API 注入 profiles 与已有系统边界。

setup 的外部退出安排、模式开关、网关和业务插件接口不变。插件升级只更新管理工具，不主动重写用户已打补丁的应用包。

## 新增真实包的维护步骤

1. 获取明确发行包，记录 exe FileVersion、完整原版 asar 摘要与大小，在隔离环境确认实际加载入口。
2. 新建独立档案和稳定 ID，按新包实测锚点、注入语义和 fuse；从本档案修订号 1 开始，不覆盖旧档案。
3. 注册新档案。构建自动携带 profiles 目录和注册表；从独立发布目录实际导入全部档案，防止源码有文件而发布包遗漏。
4. 保留旧包的识别、旧记录升级/还原回归。运行新包的无登录冷启动、官方远控不可达、网关重启恢复和 MCP 闭环；需要时增加宿主行为验证。
5. 更新支持清单与脱敏证据，说明真实验收包和限制。只有路由合成测试通过时不得宣称新 ZCode 已兼容。

## 验证与边界

- 两个同 exe 版本、不同摘要、不同入口与独立修订号的合成包，各自应用所属规则；注册顺序不影响选择。
- 格式 1 状态只读识别、从旧补丁升级、格式 1 候选应用、新格式记录及还原均覆盖。
- 跨档案候选、错误平台/ID、未知摘要、重复身份、损坏状态、未知格式与降级均拒绝；核对目标、备份及状态保持原字节。
- 真实 3.16.2 原版备份重新生成候选，其 app.asar SHA-256 必须仍为 `b9574e1235cd7d2c7b5614ed384a50a48d3c2c249e894fbacb01371913c4b784`。本次不改注入，不将管理层测试当作新一轮原生行为验收。
- 发布目录自包含导入注册表、全部档案和 CLI；已有 setup、lab 与生命周期相关测试保持通过。

不包含：自动发现并支持未知包、在线下载或执行适配代码、按语义版本区间通配、自动回滚 Desktop 版本、改造网关协议、业务插件修改以及其它平台支持。
