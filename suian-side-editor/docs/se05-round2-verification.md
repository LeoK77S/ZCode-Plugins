# SE-05 第二轮读取代际修正

范围为固定首轮提交 `ac67d05f750996c724969f4de39525273fb6bb37` 之后的唯一新增 P2。7c 到 ac 的规范轴已通过，规格轴确认首轮三项的已测触发闭合，但推演指出：规范合流接受第二份受审读取时没有推进读取代际，迟到同版本资源错误仍可能阻塞正确文件。以下是本轮实际复现与修正，新固定产物尚待根的独立窄复核；原生 H4 未验。

## 实际红灯

实际构建页通过 SDK stdio 服务恢复两份干净路径，目录链接使它们合流到同一规范目标。首份已订阅，第二次受审读在发起请求前暂停。真实 Windows ACL 拒读产生 `permission_denied` 资源回执；该旧回执在边界等待。

恢复权限与原字节后，第二次受审读取成功。测试明确核对新旧版本和 URI 均相同。最后释放旧资源错误，再切自动模式并输入，页面仍显示“系统拒绝访问该文件”、冲突条可见，保存请求为 0，磁盘正文没有写回。

首次红灯只显示等待“已保存”超时；保留原日志。为区分目标错误与夹具等待，补公开 DOM、实际请求数及磁盘诊断后再次见目标红灯。生产代码仍是 ac，没有提高超时或放松断言。

## 最小修正与绿灯

接受恢复读取结果时推进现有 `readRevision`（页面内接受读取结果的递增编号），仅新增一行更新；已有资源回执保护据此识别旧错误，并继续核对当前资源。没有增加新的持久化字段、重试或同步框架。

相同时序的契约通过：旧错误不阻塞正确恢复文件，后续自动保存取得 ACK 并核对源文件字节，干净文件之后的真实外改通知也正常刷新。测试门控只控制公开 SDK／资源边界，不触达页面私有状态或 Native 运行时。
